# ⚔️ Roadmap — Sistema de Batalla

Aquí recomiendo ser todavía más cuidadoso.

## Fase B1 — Battle Core

Primero necesitamos el corazón:

```text
Battle
├── Battler

├── BattleState
└── BattleTurn
```

Y definir:

- quién participa

- equipos
- posiciones
- turno
- fase.

---

# B2 — Battle State Machine

Probablemente será una de las piezas más importantes.

Algo parecido a:

```text
BATTLE_START
	 ↓
INTRO
	 ↓
CHOOSE_ACTION
	 ↓
RESOLVE_ACTION
	 ↓
APPLY_DAMAGE
	 ↓
CHECK_FAINT
	 ↓
CHECK_END
	 ↓
NEXT_TURN
```

Y habrá bifurcaciones para:

```text
switch
item
run
faint
multi-battle
etc.
```

No quiero que la batalla termine siendo una función gigante llena de `if`.

---

# B3 — Acciones

Crearíamos algo como:

```text
BattleAction
```

con tipos:

```text
MOVE
SWITCH
ITEM
RUN
```

Cada participante selecciona una acción.

Después el Battle System determina el orden.

## 🧭 Orden de trabajo que propondría

No necesariamente vamos a implementar todo siguiendo la lista numérica. Para evitar dependencias rotas, mi orden sería:

**Ahora:**

1. Datos de especie ✅
2. `PokemonInstance` 🟡
3. EXP / niveles
4. Stats
5. Naturaleza / IV / EV
6. Género / shiny / personalidad
7. Movimientos
8. Habilidades
9. Objetos
10. Evolución — **ya validada, ampliar después**
11. Party
12. Storage
13. Crianza / huevos

**Después batalla:**

14. Battle Core
15. Battle State Machine
16. Battlers
17. Actions
18. Turn Order
19. Type Chart
20. Damage
21. Accuracy
22. Status
23. Stat Stages
24. Weather/Terrain
25. Abilities
26. Items
27. Switching
28. Capture
29. EXP post-battle
30. AI
31. Presentation/UI

Y algo que quiero mantener como regla durante todo el desarrollo:

> **Los sistemas deben depender de datos y resultados, no de escenas ni de la UI.**

Eso nos permitirá que el mismo `PokemonInstance`, `DamageCalculator`, `EvolutionSystem`, etc. funcione desde una batalla real, un test de `EditorScript` o eventualmente desde una herramienta del editor.

Ese sería nuestro **mapa maestro**. A partir de aquí podemos ir marcando cada componente como **pendiente → en desarrollo → probado → terminado**, en lugar de saltar de sistema en sistema sin saber qué dependencias nos faltan.
